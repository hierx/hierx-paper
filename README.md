# hierx-paper

Reproducibility materials for:

> **HierX: Fast Multi-Scale Distance-Decay Interaction on Million-Node Networks**
> Alexander Hellervik, Joakim Bohlin, and Claes Andersson (2026).
> *PNAS Nexus*, pgag317. <https://doi.org/10.1093/pnasnexus/pgag317>

This repository contains benchmark scripts, data-fetching pipelines, and
pre-computed results needed to reproduce every figure and table in the paper.
It is a companion to the [`hierx`](https://github.com/hierx/hierx)
Python package, which implements the hierarchical operator itself.

## Reproducing the paper

All data and pre-computed results are archived on Zenodo for deterministic,
offline reproduction. This is the recommended path.

**DOI**: [`10.5281/zenodo.19062193`](https://doi.org/10.5281/zenodo.19062193)

### Step 1: Verify figures (quick check, < 1 minute)

```bash
git clone https://github.com/hierx/hierx-paper.git
cd hierx-paper

# Regenerate figures from pre-computed results and copy to host
docker compose run --rm hierx \
  sh -c "./reproduce.sh figures && cp -r paper_figs_final /output/"
```

Figures are written to `output/paper_figs_final/figures/`.

### Step 2: Full reproduction from Zenodo data

Fetches archived data from Zenodo, reruns all benchmarks from scratch,
regenerates figures, and verifies that reproduced results match the
pre-computed reference:

```bash
docker compose run --rm hierx \
  sh -c "./reproduce.sh reproduce && cp -r paper_figs_final /output/"
```

This runs: `data` (Zenodo fetch) → `test` → `benchmarks` → `london` →
`accessibility` → `figures` → `compare_results` (automated verification).

### Step 3: Verify reproduced results

The `reproduce` mode automatically compares every reproduced JSON result
against the pre-computed reference at the end of the run. Structural and
accuracy fields must match; timing fields are reported but not compared.

### Running individual steps

To run steps one at a time, start an interactive session so that state
(downloaded data, cached results) persists between commands:

```bash
docker compose run --rm hierx bash

# Inside the container:
./reproduce.sh data           # Fetch from Zenodo (~1.5 GB)
./reproduce.sh test           # Run hierx test suite
./reproduce.sh benchmarks     # Synthetic benchmarks (~30-60 min)
./reproduce.sh london         # London benchmarks
./reproduce.sh accessibility  # GB + London maps (~1-2 hours)
./reproduce.sh figures        # Regenerate figures
cp -r paper_figs_final /output/
exit
```

### Local install (alternative to Docker)

> **Note:** Requires Linux or macOS with Bash. On Windows, use Docker or WSL.
> Local installs are best-effort — use `requirements-lock.txt` for pinned
> versions matching the Docker image. Results may differ with other versions.

```bash
git clone https://github.com/hierx/hierx-paper.git
cd hierx-paper
pip install -r requirements-lock.txt
./reproduce.sh reproduce
```

## Fetching data from source (alternative to Zenodo)

If you prefer to regenerate data from original sources instead of using the
Zenodo archive, the following pipeline downloads census data, OSM networks,
and builds population activity vectors:

```bash
./reproduce.sh data-fetch
```

This runs six phases in sequence:

1. **Census data** (E&W + Scotland + London OA combined): `python -m benchmarks_final.fetch_census_data`
2. **London drive networks**: `python -m benchmarks_final.fetch_london_networks`
3. **London walking networks** (incl. 1.8M-node city-wide): `python -m benchmarks_final.fetch_london_walking`
4. **London population activity**: `python -m benchmarks_final.build_population_activity`
5. **GB drive network** (requires pyrosm env): `python -m benchmarks_final.fetch_uk_drive`
6. **UK population activity** (requires pyrosm env): `python -m benchmarks_final.build_uk_population_activity`

Phases 5-6 require a pyrosm/osmium conda environment:
```bash
conda create -n pyrosm python=3.12 pyrosm osmium-tool -c conda-forge
```

Note: OSM data changes over time, so results may differ slightly from the
archived snapshots. The Zenodo archive provides the exact data used in the paper.

## Zenodo archive contents

The archive contains:
- **Network snapshots** (~550 MB): `.graphml` London road/walking networks at
  various scales.
- **Census data** (~14 MB): E&W population/workplace CSVs, Scotland census,
  OA-to-LA lookup, and derived London OA combined file.
- **OA boundaries** (~208 MB): London OA boundaries (`.geojson`) and GB
  combined OA boundaries (`.gpkg`).
- **GB drive data**: GB driving network (`.pkl`) and census-derived node
  activity (`.npz`).
- **London buildings** (~304 MB): `london_buildings.gpkg` OSM building
  footprints for the London population activity pipeline.
- **London node activity** (~12 MB): `london_node_activity.npz` population
  and workplace vectors snapped to the walking network.
- **Pre-computed results** (~0.5 GB): `.npz` accessibility node arrays
  and `.json` benchmark outputs needed for accessibility figures.

Files are listed in `zenodo_manifest.txt` with SHA256 checksums.

## Interactive maps

**[Open interactive map](https://hierx.github.io/hierx-paper/interactive_maps/index.html)**
— explore accessibility results in the browser via MapLibre GL JS + PMTiles:

- **GB Driving** — 2.58M nodes, 3.02M edges (288 MB tiles)
- **London Walking** — 1.77M nodes, 1.92M edges (110 MB tiles)

Tiles are hosted on Cloudflare R2. Open `interactive_maps/index.html` in any
browser -- no server required. See
[`interactive_maps/README.md`](interactive_maps/README.md) for regeneration
and hosting details.

To regenerate tiles locally:

```bash
python interactive_maps/generate_pmtiles.py all   # requires tippecanoe
python interactive_maps/serve.py                   # local dev server at :8080
```

## Prerequisites

- Linux or macOS for local install. Any OS via Docker (recommended). Windows local install is not supported — use Docker or WSL.
- Bash, `curl` (bundled on Linux/macOS; provided in Docker image)
- Python 3.10+
- The `hierx` package (pinned to v0.1.1 in `requirements.txt`)

### Memory

Peak memory: **~240 GB** (measured via Docker on Windows/WSL2; native
Linux may use less). The `london` step dominates due to dense baseline
comparisons on the 61k-node network.

### Disk space

| Mode | Disk space | Notes |
|---|---|---|
| `figures` | ~500 MB | Docker image + pre-computed JSON results |
| `data` | ~1.5 GB | Zenodo archive download |
| `benchmarks` | ~1 GB | Synthetic benchmarks on generated grids |
| `london` | ~70 GB | Caches dense cost matrices (~29 GB drive, ~39 GB walk) |
| `accessibility` | ~2 GB | GB + London accessibility arrays |
| `reproduce` | ~75 GB | Full reproduction from Zenodo (data + benchmarks + london + accessibility) |
| `data-fetch` | ~30 GB | Full source data from OSM/Census (GB drive network is ~28 GB) |
| `maps` | ~400 MB | PMTiles vector tile archives |
| `all` | ~100 GB | Full pipeline from source (data-fetch + benchmarks + london + accessibility) |
